# Cadence — Build Prompt

Mobile-first web app, Next.js (App Router) + Tailwind + shadcn/ui, backed by Supabase.

**One patient, one condition, one loop, one brief.** No auth, no onboarding, no settings, no multi-patient. A hardcoded `PATIENT_ID` constant is the whole identity model.

---

## The thesis this app is built to demonstrate

A consultation is not an event — it's the start of an interval. Cadence captures the visit for the patient, follows the agreed plan through the weeks after by voice, and walks the patient into the next visit with a **brief** that closes the loop.

The brief is the hero. The loop is the engine. A summary alone is a memory aid; a summary plus *what actually happened across the interval* is the product.

**Hard rule:** Cadence documents and supports. It never diagnoses, prescribes, or suggests a treatment change. Every line of content traces to something a doctor said or a patient reported. If it wasn't said, it isn't there.

## Screens

### 1. Home
- Header: patient name (from a constant), condition name.
- **Timeline**, newest first — one card per event, three kinds:
  - **Visit** — date, care setting, one-line diagnosis preview.
  - **Check-in** — date, one-line outcome ("Amitriptyline: still taking it, sleep better").
  - **Brief** — date, "Next-visit brief" with a distinct accent.
- **Open commitments** panel at top: the live checklist of what was agreed, each with status (`pending` / `done` / `not_done` / `changed`). This panel is the app's pulse — it should be the first thing the eye lands on.
- Two buttons: **+ Record a visit** and **Generate next-visit brief** (enabled once ≥1 visit exists).

### 2. New visit
- Care setting dropdown: GP / Hospital / Emergency / Specialist. Optional: clinician name, organisation.
- Date, defaults to today.
- Required checkbox, gates the record button: ☐ *"My clinician has agreed to this consultation being recorded."*
- Big **Record** button using MediaRecorder. Timer, stop button, playback to review, then **Process recording**.
- **Fallback path (protect the demo):** a "Paste transcript instead" link that skips straight to processing with pasted text. Live audio is the nice version; the loop is the point.

### 3. Processing
- POST audio to `/api/transcribe` → ElevenLabs Scribe (`scribe_v1`, speaker diarization on, `ELEVENLABS_API_KEY`).
- Transcript → `/api/summarise` → Claude (`ANTHROPIC_API_KEY`, `claude-sonnet-5`) with the prompt and schema below.
- Persist transcript + structured JSON + extracted commitments to Supabase.
- Loading states: "Transcribing your consultation…" → "Organising your summary…" → "Finding what you agreed…".

### 4. Visit summary
Render the JSON as calm, patient-friendly cards, in order:

1. **Your symptoms**
2. **Doctor's diagnosis**
3. **Doctor's advice**
4. **⚠️ Red flags — when to go back** (bullets, amber/red, visually prominent)
5. **Medications** — one card each: name, dosage, frequency, duration, instructions
6. **What to avoid**
7. **Lifestyle advice**
8. **What you agreed** — the commitments list, each with type icon and timeframe. *This is the new section and the bridge to the loop.*
9. Collapsible **View full transcript**

Persistent footer: *"This summary only reflects what was said during your appointment. It is not medical advice. If you're unsure about anything, contact your clinician."*

### 5. Voice check-in — the loop
Reached from a **Check in now** button on Home (and, in a real deployment, a scheduled nudge — out of scope here).

- An **ElevenLabs Agent** conversation. The agent opens with a warm one-liner, then walks the open commitments one at a time: *"Six weeks ago you agreed to try amitriptyline at night. How's that going?"* / *"Did the blood test happen?"* / *"You were told to come back if the dizziness returned — has it?"*
- The agent's system prompt is built at runtime from the open commitments (inject them as context). It asks, listens, acknowledges. **It does not advise.** If the patient asks what to do, it says that's for their clinician and offers to note the question for the brief.
- Keep it short — 60–90 seconds. Fatigue is the core symptom of this population.
- On end, the transcript goes to `/api/checkin` → Claude, which maps what was said onto the open commitments and returns outcomes (below). Persist; update commitment statuses.
- **Text fallback:** a plain form listing open commitments with status + free-text note, for when the mic or the Agent fails.

### 6. Next-visit brief — the hero
Generated by `/api/brief` from: the visit summary, the commitments, and every check-in outcome in the interval. Four sections, in this order and with this framing:

| Section | Content |
| --- | --- |
| **What we agreed** | Each commitment, as stated at the visit. |
| **What I did** | Per commitment: done / not done / partially — with the patient's own words. Not-done is stated plainly, never softened. |
| **What happened** | Symptoms, side effects, events reported across the check-ins, with rough timing ("week 2: sleep improved; week 5: dizziness returned twice"). |
| **What changed** | The delta since the visit — what's better, worse, unchanged, and any open question the patient wants to ask. |

- Full-width, printable/shareable, designed to be **handed to a doctor**. A "Share / Save PDF" button.
- Header line: *"Prepared by the patient from recorded consultations and self-reported check-ins."* — that sentence is the regulatory framing, keep it.
- Footer disclaimer as above.
- If no check-ins exist yet, the brief must say so explicitly rather than pad. Empty interval is honest output.

### 7. Demo time-compression (build this, it's load-bearing on stage)
A small **dev drawer** (a floating button, visible only when `NEXT_PUBLIC_DEMO_MODE=true`):
- "Advance clock" — offsets displayed timestamps so check-ins read as week 2 / week 5 rather than all today.
- "Seed demo state" — loads a canned visit + commitments so the loop can be shown without recording.

Three minutes on stage cannot contain six real weeks. Compressing the interval is a feature of the demo, not a cheat — say so.

## LLM calls

All three return **JSON only**. Prompt for it, parse defensively, log the raw response on failure.

### A. Visit summary + commitment extraction — `/api/summarise`

System prompt (verbatim):

```
You are a medical scribe assistant working for the PATIENT, not the clinician.
You will receive a transcript, generated from an audio recording, of a
consultation between a patient and a doctor.

Identify who is speaking (DOCTOR or PATIENT), then organise ONLY what was
actually said into the JSON structure below.

Rules:
- Do not add, infer, or invent any medical information.
- Do not give advice of your own. You are recording what was said, nothing more.
- If something was not mentioned in the transcript, return "" or [].
- Capture medication names, dosages, durations, and timings EXACTLY as the
  doctor states them. If a dosage is unclear or inaudible, write
  "unclear — please confirm with your doctor" rather than guessing.
- Extract COMMITMENTS: the concrete things the patient and doctor agreed would
  happen before the next visit. A commitment is trackable — something that can
  later be answered "did this happen?". Examples: starting a medication,
  getting a test, watching for a symptom, booking a follow-up. Prose advice
  with no action is not a commitment.
- Write in plain, patient-friendly language.
- Return valid JSON only, matching the schema. No markdown, no commentary.
```

Schema:

```json
{
  "patient_symptoms_summary": "string",
  "doctor_diagnosis": "string",
  "doctor_advice": "string",
  "red_flags": ["string"],
  "medications": [
    { "name": "", "dosage": "", "frequency": "", "duration": "", "instructions": "" }
  ],
  "things_to_avoid": ["string"],
  "lifestyle_advice": ["string"],
  "commitments": [
    {
      "text": "string — what was agreed, in the patient's second person",
      "type": "medication | test | watch_for | followup | lifestyle",
      "timeframe": "string — as stated, e.g. '6 weeks', 'before next visit', ''",
      "source_quote": "string — the line in the transcript this came from"
    }
  ],
  "future_plan": {
    "follow_up_needed": true,
    "date_or_timeframe": "string",
    "purpose": "string"
  }
}
```

`source_quote` matters — it's the audit trail proving the loop is made of real data.

### B. Check-in mapping — `/api/checkin`

Input: the check-in transcript + the list of open commitments (id + text).

System prompt (verbatim):

```
You are processing a short voice check-in between a patient and a health
companion app. You will receive the check-in transcript and a list of
commitments the patient made at their last consultation.

For each commitment, decide from the transcript alone what happened. Use the
patient's own words wherever possible.

Rules:
- Only report what the patient actually said. If a commitment was not
  discussed, status is "unknown" and the note is "".
- Never judge, advise, or suggest a change. You are recording, not deciding.
- Also capture anything the patient reported that was NOT tied to a
  commitment: new symptoms, side effects, events, or questions they want to
  ask their doctor.
- Return valid JSON only. No markdown, no commentary.
```

Schema:

```json
{
  "outcomes": [
    {
      "commitment_id": "string",
      "status": "done | not_done | partial | changed | unknown",
      "patient_words": "string — quoted or closely paraphrased",
      "note": "string"
    }
  ],
  "unprompted_reports": ["string"],
  "questions_for_doctor": ["string"]
}
```

### C. Next-visit brief — `/api/brief`

Input: visit summary JSON, commitments with current status, all check-in outcomes with their dates.

System prompt (verbatim):

```
You are preparing a brief that a PATIENT will hand to their DOCTOR at their
next appointment. You will receive: a summary of the last consultation, the
commitments agreed at it, and the outcomes of voice check-ins across the
interval since.

Write four sections: what we agreed, what I did, what happened, what changed.

Rules:
- Every statement must trace to the input. Invent nothing.
- Where a commitment was not kept, say so plainly and without apology or
  euphemism. That is the useful signal for the doctor.
- Where data is missing, say it is missing. Do not pad.
- Do not diagnose, do not suggest treatment, do not recommend a course of
  action. Report the interval; the doctor decides.
- Use rough timing where the check-in dates support it ("around week two").
- Write for a clinician reading in under a minute: dense, specific, no filler.
- Return valid JSON only. No markdown, no commentary.
```

Schema:

```json
{
  "agreed": [{ "commitment_id": "", "text": "" }],
  "did": [{ "commitment_id": "", "text": "", "status": "done | not_done | partial | changed | unknown" }],
  "happened": [{ "text": "", "approx_timing": "" }],
  "changed": [{ "text": "", "direction": "better | worse | unchanged | unclear" }],
  "open_questions": ["string"],
  "gaps": ["string — what the record does not cover"]
}
```

## Data model (Supabase, Postgres)

RLS on, single hardcoded patient. `pgvector` column on `visits.embedding` — unused by this build, present to show the longitudinal record it becomes.

```
patients      id, name, created_at
conditions    id, patient_id, name, status, created_at
visits        id, condition_id, date, care_setting, clinician_name,
              organisation, transcript, summary jsonb, embedding vector,
              created_at
commitments   id, visit_id, text, type, timeframe, source_quote,
              status default 'pending', created_at
check_ins     id, condition_id, date, transcript, raw jsonb, created_at
outcomes      id, check_in_id, commitment_id, status, patient_words, note
briefs        id, condition_id, generated_at, content jsonb
```

`commitments.status` is denormalised from the latest outcome — the Open Commitments panel reads it directly.

## Consent & safety (minimal, real)

Not a screen. Not an onboarding flow.

- The **recording-consent checkbox** on the new-visit screen — the clinician is a data subject too, this one is non-optional.
- The **persistent disclaimer** on every summary, check-in, and brief.
- A **Delete everything** link in the Home footer: confirmation dialog, then cascade-delete the patient's rows.

That's it. Data minimisation by having almost no fields, not by having a consent wizard.

## Design

- Mobile-first, max-width container, large touch targets.
- Calm palette: soft blues/greens, white cards, generous spacing.
- Red flags: amber/red accent. Everything else stays reassuring.
- **The brief gets a different visual register** — denser, more document-like, less app-like. It's meant to look like something you print and hand over.
- Voice check-in screen: near-empty. A waveform, the agent's current question in large type, nothing else.

## Build order (36h — cut from the bottom)

1. Supabase schema + hardcoded patient + Home timeline reading from it.
2. Paste-transcript → Claude summary + commitment extraction → summary screen. **The loop's foundation; do not skip to audio first.**
3. Text-form check-in → outcome mapping → commitment statuses update on Home.
4. **The brief.** Everything above exists to make this real.
5. ElevenLabs Scribe recording path (replacing paste as the primary route).
6. ElevenLabs Agent voice check-in (replacing the text form as the primary route).
7. Demo drawer / time compression.
8. Share-as-PDF, polish.

Steps 1–4 are the product. 5–6 are the sponsor depth and the stage magic. If a dependency eats more than 30 minutes, cut to the fallback and move on.
